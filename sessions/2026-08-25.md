### Findings confirmed so far (this session, 2026-08-25)

1. **Baseline reproduced live**: fresh quote, Age=35/Male, Occupation Code=AM (plain
   select, "Occupation" type-ahead left untouched), click Needlestick → cover activates
   successfully (a "Needlestick A" card with Sum Insured + "Remove" link appears). This
   matches the automated test's finding — no gating happens.

2. **Clicking Apply afterward does NOT remove/block the already-active cover.** The
   Needlestick button becomes `disabled` (consistent with "can't re-toggle something
   already active", not with a gating rule firing), but the cover card stays. No
   occupation-related error/banner appeared anywhere on the page.
   - **Confound**: 2 console errors fired around Apply — both server-side 500s, one from
     an apparently-unrelated `ECT_Provider/WS_ECT.asmx` endpoint, one a generic
     `OutSystemsUI.controller.js` internal error. It's possible Apply's request chain
     broke on that unrelated 500 before reaching any occupation-eligibility check —
     so this result is **inconclusive**, not a clean "Apply doesn't enforce it" result.

3. **Populating the "Occupation" type-ahead field DOES auto-fill and lock "Occupation
   Code"** (confirms existing PD-07/PD-08 docs about the relationship between these two
   fields). But:
   - Searching "Armed Forces" in the type-ahead offers exactly two options —
     "Armed Forces - all ranks - office/admin duties only" and "Armed Forces Personnel"
     — and **both resolve to Occupation Code = U, not AM**. So the assumption baked into
     the original bug report / LSC-02/03 docs ("AM = Armed Forces") could not be
     re-tested directly through the type-ahead — I never found a type-ahead entry that
     actually maps to AM.
   - In both cases (mapping to U), the already-active Needlestick cover **still was not
     removed** even after Occupation Code silently changed underneath it. Same
     no-retroactive-validation behavior as the Apply-click test.
   - Consequence: I still don't have a confirmed case of "Occupation type-ahead
     populated AND Occupation Code = AM specifically" — every attempt at that combination
     via the type-ahead landed on U instead of AM.

## RESOLUTION (later same day, after restart)

The open question above is now resolved — not by finding an AM-mapping type-ahead entry
(none exists among any plausible search term), but by running the full matrix instead of
guessing at one more combination:

- **Full sweep**: every Occupation Code (blank, AM, AA, A1, A2, B, C, S, U, IC) × all 4
  gated covers (Needlestick, Cancer, Acd. Death, Specific Injury), one fresh quote per
  code, via the plain select. **All 40 combinations activated — zero gating anywhere.**
  Two apparent exceptions mid-sweep (OCC=C button-not-found, OCC=IC Cancer no-op) did not
  reproduce on retest with more settle time — both were probe-timing flakes, not real gates.
- **Type-ahead hunt**: searched every plausible Armed-Forces/military term
  (Army/Navy/Air Force/Military/Soldier/Defence/Defense/NZDF/Combat/Infantry/Marine/Armed
  Forces) in the "Occupation" type-ahead. Only "Armed Forces" and "Marine" returned any
  results; none of the 10 titles found resolve to AM — the two Armed-Forces titles both
  resolve to **U**. Selected U (and, as a control, an AA-resolving title) via the
  type-ahead and retested Needlestick/Cancer with no Apply click involved at all — both
  activated in both cases. **This conclusively rules out the "gating only fires via the
  type-ahead / after Apply" hypothesis** — same broken result either way.

**Conclusion:** this is a real, comprehensively-confirmed, unresolved regression (or
undocumented intentional removal — not yet confirmed with BA/PM either way) affecting
`LSC-02`/`LSC-03` occupation gating across every code and every input path. Not an
AM-specific issue and not a test-methodology gap.
