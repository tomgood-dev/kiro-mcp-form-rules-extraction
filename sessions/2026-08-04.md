## Key things we discovered

**The biggest one:** OutSystems doesn't respond to standard Playwright `fill()` or
`label.click()`. You have to interact the way a real user would — keyboard events for
text inputs (`type` action in server.js), and actual mouse coordinates for checkboxes,
radios, and button groups (scrollIntoView then mouse-click at the exact viewport position).
We confirmed this by watching fields that looked filled in the DOM but OutSystems
hadn't registered the value — clicking Next would silently stay on the page.

**Checkboxes and radios:** `label.click()` registers in the DOM but OutSystems ignores it.
Had to scroll the `<input>` element into view, get its bounding rectangle, then
fire `page.mouse.click(x, y)`. This is now the standard pattern.

**Button groups:** Same story — `<button class="button-group-item">` elements need the
same scrollIntoView + mouse-click treatment.

**Element IDs regenerate:** OutSystems rebuilds them on every render. An ID that worked
five minutes ago may be different after a page interaction. Always re-query.

**The tobacco question on page 7 is a `<select>`,** not a radio like every other
Yes/No on that page. Easy to miss.

**Personal Statement loops back to page 1** if any question is unanswered anywhere in
the 7 pages. There's an unanswered questions summary page at `UnderwritingSummary?l=1`
that lists everything outstanding with Answer buttons linking to the right page.

**Policy owner Add button:** This caught us — after selecting an owner from the dropdown,
you still have to click Add. Without it you get a validation error on Next. Selecting
from the dropdown alone does nothing.
